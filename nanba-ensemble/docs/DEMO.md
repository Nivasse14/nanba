# Démonstration locale des huit modules

Tout ce scénario utilise exclusivement les comptes et données synthétiques. Chaque action passe par les mêmes API et transactions que l’application.

1. **Collectif.** Profil Membre → Proposer une idée → compléter titre, description, créneau, seuil 2 et échéance future. Cliquer « Ça m’intéresse ». Changer de profil → Admin → retrouver la demande → Valider le sondage. Administration → Traiter la file : statut **Simulé**. Revenir à la demande → Simuler un vote avec une identité fictive. Profil Professionnel → Espace professionnel → demande → Préparer une offre → confirmer l’offre. Profil Membre → offre → M’inscrire → cocher l’accord sur la version affichée. Redémarrer : compteur et inscription persistent.
2. **Rencontre.** Profil Organisateur → Petites rencontres → créer capacité 2 et coordination. Profil Membre → inscription 2 adultes ; l’adresse de coordination devient visible. Autre membre → inscription en attente. Le premier se désiste : le suivant voit une place proposée à accepter, pas une réservation imposée. Export ICS disponible.
3. **Logement.** Profil Membre → recherche privée → choisir Atelier & Habitat. Profil Professionnel → lire cette seule recherche, proposer une référence d’annonce et sa date réelle de disponibilité. L’autre professionnel et l’admin ne la voient pas. Le membre peut demander un contact puis retirer l’autorisation ; le professionnel perd immédiatement l’accès. Une disponibilité datant de plus de 7 jours apparaît « à reconfirmer ».
4. **Entraide.** Le profil Organisateur dispose d’un profil volontaire synthétique CV/Conversation. La demande « Un regard sur mon CV » a un créneau compatible. Le volontaire se propose ; le membre accepte. Un autre engagement qui se chevauche est refusé. Annulation : le créneau est de nouveau disponible. Les nouvelles demandes nécessitent un créneau futur.
5. **Radar.** Membre → soumettre une observation avec lieu et heure. Admin → relire et publier ; la provenance reste « membre ». Pour confirmer, fournir la provenance obtenue et le justificatif. Une contestation enlève l’item des informations actuelles. L’expiration est démontrée avec une horloge contrôlée dans les tests, sans attendre 24 heures.
6. **Arrivants.** Membre → rejoindre une cohorte en acceptant sa version → cocher des étapes, sauvegarder une ressource, rattacher une rencontre déjà rejointe, choisir son thème et éventuellement proposer son mentorat. Changer de membre : la progression précédente n’est pas affichée.
7. **Défi.** Admin → créer question, choix, réponse attendue et sources → vérifier. Membres → choisir Paris/Lyon pendant l’inscription. Admin → figer les équipes et ouvrir. Chacun répond une fois. La clôture est permise uniquement après l’échéance. Le test utilise une horloge contrôlée ; le classement est recalculable et la carte SVG ne contient que les équipes.
8. **Récit.** Membre → original + traduction → relire et valider les droits, le texte et les canaux. Avant cela, aucun autre membre ni admin ne lit le brouillon. Admin → publier sur Nanba ; le partage WhatsApp exige l’accord distinct. Carte SVG téléchargeable. L’auteur peut retirer : disparition des surfaces Nanba et annulation de la file d’envoi en attente. Les copies externes déjà partagées ne sont pas garanties supprimées.

Pour tester Jules/Priya ou le professionnel non autorisé, utiliser les adresses de démonstration du README dans le formulaire de connexion, avec le mot de passe de démonstration.

Les parcours difficiles (simultanéité, doublons, ordre des votes, indisponibilité, expiration) sont reproductibles par `npm test`, sans connexion de compte réel.
